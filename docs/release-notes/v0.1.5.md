# TM Publisher 0.1.5

[English](#english) · [Türkçe](#türkçe)

## English

One program file, and nothing runs between your posts. Your data does not change; see **Update** below (from 0.1.3–0.1.4,
quit the old scheduler first, then delete its files).

### What changed since 0.1.4

- **One program file per platform.** Windows: `TMPublisher.exe`; Linux: `tm-publisher`. The .NET runtime and every native
  library (SQLite3 Multiple Ciphers, Skia, HarfBuzz) are inside it; the archives hold only it and the documents
  (README, LICENSE, third-party notices, font licenses). `TMPublisherScheduler.exe` / `tm-publisher-scheduler` and
  `sqlite3mc.dll` / `libsqlite3mc.so` are gone.
- **No always-running scheduler, no tray icon.** While the window is open, it sends the scheduled posts itself. While it is
  closed, your system's scheduler starts the program for a moment with `--run-due`: it opens the database with the keyring,
  sends every post whose time has come, sets the next start and ends. Between posts no TM Publisher process runs.
  - Windows: a **Task Scheduler** task of your user (`TM Publisher <code>`), no administrator rights: a start at the next post's
    time, safety starts 30, 60 and 120 minutes after it (in case a run ended before it set the next start), a start one minute
    after you sign in; missed starts run as soon as the computer is back; a run longer than an hour is stopped.
  - Linux: a **systemd user timer** and service (`tm-publisher-<code>`), only calendar times (the post's time and the same three
    safety starts), `Persistent=true` for starts missed while the computer was off. Without a systemd user session, posts are
    sent only while the window is open (a post whose time passes while it is closed waits for you); Settings says so.
  - The same rules as before: a post is claimed in the database before it is sent, it is never sent twice, a post more than
    5 minutes late waits for you, errors are retried after 1, 2, 4, 8, then 15 minutes (also a run that cannot open the
    database, for example when the keyring does not answer), posts are sent one account at a time.
  - Only one sender works per data folder: while the window is open a run ends at once, two runs never overlap.
  - A run's notifications (published, failed, missed) appear in the bottom-right corner as before. On Linux the service has
    `KillMode=process`, so systemd leaves the notification process running after the run ended.
  - Closing the window while a post is being sent does not cut the upload off: the program finishes it without a window (at most
    an hour), then sets the next start; only a shutdown or sign-out gets the short 15-second wait.
  - With the window open, a post that falls due soon after the computer wakes (or is woken by the task) is sent at its time: the
    window looks at the clock every minute, because a system timer does not count the time asleep.
- **Settings:** "Send scheduled posts while TM Publisher is closed" (on by default) writes or removes the task / timer; "Wake
  the computer from sleep to send a post" (Windows, off by default); the **Sending** card shows who sends now, the next post and
  when the system starts TM Publisher next; **Pause scheduling** also holds the runs while the window is closed.
- **Master password:** a run cannot ask for it, so nothing is sent while the app is closed. At each post's time (the next 20 posts
  the window knew when it closed) a notification asks you once to open TM Publisher; unlock it within 5 minutes of the post's time
  and the window sends it, later it waits for you.
- **Update from 0.1.0–0.1.4 by itself:** the old autostart entry of the same data folder (Windows Run key, Linux
  `~/.config/autostart/tm-publisher.desktop`) is removed at the first start, and a 0.1.3–0.1.4 scheduler that still runs on the
  same data folder is asked to quit (a post it is sending is finished first). Both are logged.
- **Logs:** a run writes `logs/run-yyyy-MM-dd.log`; its last line gives how long it took, its peak memory and that no UI library
  was loaded. The rules of 0.1.4 stay (7 days, masked, Information and above). The logs zip now names the system scheduler
  entry's state and whether the old scheduler file is still next to the program.
- The release archives are smaller (Windows 23.0 → 18.2 MiB, linux-x64 30.0 → 16.4 MiB, linux-arm64 20.8 → 15.8 MiB).

### Measured

Release files of this version, each run with its own data folder: 3 posts due on an account of a platform the program does not
know (they are blocked before any request, so nothing reaches the network) and 1 post two hours ahead; notifications off. The
run's own last log line (peak working set on Windows, `VmHWM` peak RSS on Linux) and the wall time around the process.

| | Duration of one run | Peak memory |
|---|---|---|
| Windows 11 x64, 3 posts due (4 runs) | 1.5–1.7 s (1.7–1.9 s wall) | working set 49.4–49.8 MB, private 15.0–16.0 MiB |
| Windows 11 x64, nothing due | 0.9 s | working set 47.2 MB |
| Raspberry Pi 5 (arm64), no database yet (3 runs) | 0.6 s (0.7 s wall) | RSS 42.5 MB |
| Raspberry Pi 5, master-password database, posts due (2 runs) | 0.8 s (0.9 s wall) | RSS 45.8 MB |
| Raspberry Pi 5, 3 posts due, the same run code in a measurement tool (not the release file) that first opens the master-password database (3 runs) | 2.7 s, of it 1.1 s opening with the master password | RSS 141 MB, most of it the master-password key derivation (Argon2id) the keyring run does not do |

Between posts: no TM Publisher process (checked with Task Manager's process list and `pgrep`); the Task Scheduler task shows
the next run time (Windows), `systemctl --user list-timers` shows the timer (Linux), and on the Pi the timer started the program
by itself at the post's time (journal: "Finished tm…service"). A Raspberry Pi without `secret-tool` uses a master password, so
the release file there cannot send while closed; the keyring run was measured on Windows. For comparison, 0.1.4 kept a
scheduler running all the time (Windows Task Manager 5.6 MB, working set ~20 MB; Pi RSS ~19 MB).

### Known limits

- With a master password nothing is sent while the app is closed (one notification per due post asks you to open it, for the
  next 20 posts the window knew).
- A start missed while the computer was asleep runs when it wakes; a post found more than 5 minutes late then waits for you (as
  before, when the computer was asleep at the post's time). Waking the computer for a post is a Windows option, off by default.
- Linux: the run needs your keyring, so it sends only while you are signed in; lingering does not change that (the keyring stays
  locked). Notifications of a run need the desktop's `DISPLAY` / `WAYLAND_DISPLAY` in the systemd user environment
  (`systemctl --user import-environment DISPLAY WAYLAND_DISPLAY`).
- Linux: that the notification process outlives the run with `KillMode=process` was checked with systemd 257 on the Pi (a child
  of a one-shot unit); the measurements below ran with notifications off.
- Moving the program file: open it once from the new place so the task / timer points there.
- The platform limits are unchanged.

### Update

1. Optional: Settings → Backup.
2. From 0.1.3–0.1.4: close the window and quit the scheduler (tray icon → Quit, or Settings → Stop). From 0.1.0–0.1.2: quit it
   from its tray.
3. Windows: unpack the zip over the `TM Publisher` folder and delete `TMPublisherScheduler.exe` and `sqlite3mc.dll` there. Linux:
   unpack over the `tm-publisher` folder and delete `tm-publisher-scheduler` and `libsqlite3mc.so`.
4. Start TM Publisher once. It removes the old autostart entry and writes the task / timer.

## Türkçe

Tek program dosyası; gönderileriniz arasında hiçbir şey çalışmaz. Verileriniz değişmez; aşağıdaki **Güncelleme**'ye bakın
(0.1.3–0.1.4'ten: önce eski zamanlayıcıdan çıkın, sonra dosyalarını silin).

### 0.1.4'ten bu yana değişenler

- **Platform başına tek program dosyası.** Windows: `TMPublisher.exe`; Linux: `tm-publisher`. .NET çalışma ortamı ve bütün yerel
  kitaplıklar (SQLite3 Multiple Ciphers, Skia, HarfBuzz) içindedir; arşivlerde yalnız o ve belgeler (README, LICENSE, üçüncü
  taraf bildirimleri, yazı tipi lisansları) vardır. `TMPublisherScheduler.exe` / `tm-publisher-scheduler` ve `sqlite3mc.dll` /
  `libsqlite3mc.so` kalktı.
- **Sürekli çalışan zamanlayıcı ve tepsi simgesi yok.** Pencere açıkken zamanlanmış gönderileri kendisi gönderir. Kapalıyken
  sisteminizin zamanlayıcısı programı `--run-due` ile kısa bir süre için başlatır: veritabanını anahtarlıkla açar, saati gelen her
  gönderiyi gönderir, sonraki başlatmayı ayarlar ve kapanır. Gönderiler arasında hiçbir TM Publisher süreci çalışmaz.
  - Windows: kullanıcınızın bir **Görev Zamanlayıcı** görevi (`TM Publisher <kod>`), yönetici izni gerekmez: sıradaki gönderinin
    saatinde bir başlatma, o çalıştırma sonrakini ayarlamadan kapandıysa diye 30, 60 ve 120 dakika sonra güvenlik başlatmaları,
    oturum açtıktan bir dakika sonra bir başlatma; kaçan başlatmalar bilgisayar dönünce hemen yapılır; bir saatten uzun süren
    çalıştırma durdurulur.
  - Linux: bir **systemd kullanıcı zamanlayıcısı** ve hizmeti (`tm-publisher-<kod>`), yalnız takvim saatleri (gönderinin saati ve
    aynı üç güvenlik başlatması), bilgisayar kapalıyken kaçan başlatmalar için `Persistent=true`. systemd kullanıcı oturumu yoksa
    gönderiler yalnız pencere açıkken gider (saati pencere kapalıyken geçen gönderi sizi bekler); Ayarlar bunu söyler.
  - Kurallar önceki gibi: gönderi göndermeden önce veritabanında üstlenilir, asla iki kez gitmez, 5 dakikadan fazla gecikmiş
    gönderi sizi bekler, hatalar 1, 2, 4, 8, sonra 15 dakika sonra yeniden denenir (veritabanını açamayan çalıştırma da, örneğin
    anahtarlık yanıt vermeyince), hesaplara tek tek gönderilir.
  - Bir veri klasöründe aynı anda tek gönderici çalışır: pencere açıkken çalıştırma hemen kapanır, iki çalıştırma üst üste gelmez.
  - Çalıştırmanın bildirimleri (yayınlandı, başarısız, kaçırıldı) önceki gibi sağ alt köşede görünür. Linux'ta hizmette
    `KillMode=process` var; systemd bildirim sürecini çalıştırma bittikten sonra da çalışır bırakır.
  - Bir gönderi giderken pencereyi kapatmak yüklemeyi yarıda kesmez: program onu penceresiz bitirir (en çok bir saat), sonra
    sonraki başlatmayı ayarlar; kısa 15 saniyelik bekleme yalnız kapanış ya da oturum kapatmada.
  - Pencere açıkken bilgisayar uyandıktan kısa süre sonra (ya da görev onu uyandırınca) saati gelen gönderi saatinde gider: sistem
    zamanlayıcısı uykuda geçen süreyi saymadığı için pencere saate her dakika bakar.
- **Ayarlar:** "TM Publisher kapalıyken de zamanlanmış gönderileri gönder" (varsayılan açık) görevi / zamanlayıcıyı yazar ya da
  siler; "Bir gönderiyi göndermek için bilgisayarı uykudan uyandır" (Windows, varsayılan kapalı); **Gönderme** kartı şu an kimin
  gönderdiğini, sıradaki gönderiyi ve sistemin TM Publisher'ı ne zaman başlatacağını gösterir; **Zamanlamayı duraklat** pencere
  kapalıyken çalıştırmaları da durdurur.
- **Ana parola:** çalıştırma parolayı soramaz; program kapalıyken hiçbir şey gönderilmez. Her gönderinin saatinde (pencerenin
  kapanırken bildiği sonraki 20 gönderi) bir bildirim TM Publisher'ı açmanızı bir kez ister; gönderinin saatinden sonraki 5 dakika
  içinde kilidi açarsanız gönderiyi pencere gönderir, daha sonra açarsanız gönderi sizi bekler.
- **0.1.0–0.1.4'ten kendiliğinden geçiş:** aynı veri klasörünün eski otomatik başlatma kaydı (Windows Run anahtarı, Linux
  `~/.config/autostart/tm-publisher.desktop`) ilk açılışta silinir; aynı veri klasöründe hâlâ çalışan 0.1.3–0.1.4 zamanlayıcısından
  kapanması istenir (gönderdiği gönderi önce biter). İkisi de günlüğe yazılır.
- **Günlükler:** çalıştırma `logs/run-yyyy-MM-dd.log` yazar; son satırı süreyi, en yüksek belleği ve hiçbir arayüz kitaplığının
  yüklenmediğini söyler. 0.1.4 kuralları sürer (7 gün, gizleme, Information ve üstü). Günlük zip'i artık sistem zamanlayıcısı
  girdisinin durumunu ve eski zamanlayıcı dosyasının programın yanında durup durmadığını yazar.
- Sürüm arşivleri küçüldü (Windows 23,0 → 18,2 MiB, linux-x64 30,0 → 16,4 MiB, linux-arm64 20,8 → 15,8 MiB).

### Ölçüm

Bu sürümün dosyaları, her çalıştırma kendi veri klasörüyle: programın tanımadığı bir platformdaki hesaba saati gelmiş 3 gönderi
(hiçbir istekten önce engellenir, ağa bir şey gitmez) ve iki saat sonraya 1 gönderi; bildirimler kapalı. Çalıştırmanın kendi son
günlük satırı (Windows'ta en yüksek çalışma kümesi, Linux'ta `VmHWM` en yüksek RSS) ve süreç çevresinde ölçülen süre.

| Windows 11 x64, saati gelen yok | 0,9 sn | çalışma kümesi 47,2 MB |
| Raspberry Pi 5 (arm64), henüz veritabanı yok (3 deneme) | 0,6 sn (dışarıdan 0,7 sn) | RSS 42,5 MB |

Gönderiler arasında: hiçbir TM Publisher süreci yok (Görev Yöneticisi süreç listesi ve `pgrep` ile bakıldı); Görev Zamanlayıcı
görevi sonraki çalışma saatini gösteriyor (Windows), `systemctl --user list-timers` zamanlayıcıyı gösteriyor (Linux) ve Pi'de

Raspberry Pi ana parola kullanır; orada sürüm dosyası kapalıyken gönderemez; anahtarlıklı çalıştırma Windows'ta ölçüldü.
Karşılaştırma: 0.1.4'te bir zamanlayıcı sürekli çalışıyordu (Windows Görev Yöneticisi 5,6 MB, çalışma kümesi ~20 MB; Pi RSS ~19 MB).

### Bilinen kısıtlar

- Ana parolayla program kapalıyken hiçbir şey gönderilmez (saati gelen her gönderi için bir bildirim açmanızı ister; pencerenin
  bildiği sonraki 20 gönderi için).
- Bilgisayar uykudayken kaçan başlatma uyanınca yapılır; 5 dakikadan fazla gecikmiş bulunan gönderi o zaman sizi bekler (önceden
  de bilgisayar gönderinin saatinde uykudaysa böyleydi). Gönderi için bilgisayarı uyandırmak bir Windows seçeneğidir, varsayılan kapalı.
- Linux: çalıştırma anahtarlığınıza ihtiyaç duyar; bu yüzden yalnız siz oturum açmışken gönderir, `loginctl enable-linger` bunu
  değiştirmez (anahtarlık kilitli kalır). Çalıştırmanın bildirimleri için masaüstünün `DISPLAY` / `WAYLAND_DISPLAY` değeri systemd
  kullanıcı ortamında olmalı (`systemctl --user import-environment DISPLAY WAYLAND_DISPLAY`).
- Linux: bildirim sürecinin `KillMode=process` ile çalıştırmadan sonra yaşadığı Pi'de systemd 257 ile denendi (tek seferlik bir
  birimin alt süreci); aşağıdaki ölçümler bildirimler kapalıyken yapıldı.
- Program dosyasını taşırsanız yeni yerinden bir kez açın; görev / zamanlayıcı oraya yönelir.
- Platform kısıtları değişmedi.

### Güncelleme

1. İsteğe bağlı: Ayarlar → Yedek.
2. 0.1.3–0.1.4'ten: pencereyi kapatın ve zamanlayıcıdan çıkın (tepsi simgesi → Çık ya da Ayarlar → Durdur). 0.1.0–0.1.2'den:
   tepsisinden çıkın.
3. Windows: zip'i `TM Publisher` klasörünün üzerine açın ve oradaki `TMPublisherScheduler.exe` ile `sqlite3mc.dll`'yi silin.
   Linux: `tm-publisher` klasörünün üzerine açın ve `tm-publisher-scheduler` ile `libsqlite3mc.so`'yu silin.
4. TM Publisher'ı bir kez başlatın. Eski otomatik başlatma kaydını siler, görevi / zamanlayıcıyı yazar.
